**2^5 SOLVED for the first time -- 2026-08-06, ~180,000 GA.** The long-standing holy grail. Reproducible (user's main PC overheats on 2^5; ran on a newer laptop -- ~15 min of pure compute there, realistically ~2x wall-clock). REPEATS on the same config (0% seed, Floor 4): ~180k and ~240k -> run-to-run spread ~30%, so a SINGLE 2^5 run cannot compare configs (any delta < ~30-40% is noise). A Floor=2 + Seed=75 run gave ~280k but changed TWO vars at once (confounded) AND Seed adds pure host-side seed-build time, not search -- inconclusive. Rule: tune seeds/Floor on the CHEAP 2^4 batch, one variable at a time; don't burn 2^5 single-runs on it. (Two earlier ~100k "solves" were descent flukes -- the peel occasionally jumps 1+1->solved -- not the ladder.) Milestone alongside [[unified-evaluator-direction]]; the tail it exposes is [[endgame-tail-is-findability]].

**Exact params of the solve:**
- SEED_RATIO = **0%** (no seeding). Consistent with the 2^4 seed-sweep (2026-08-06): on 2^4 seeds barely help gens and cost ~5-7x host time; raw SEED_RATIO=100 was WORST on every axis (floods the pool with near-identical raw seeds -> kills crossover diversity). So 0% is the current default. See [[seeder-role-boundary]].
- Population = 2048.
- Floor = 4.
- Descent: at/below Floor the base error is multiplied by `Floor/scrambled` (`local_fA_sum *= FLOOR/scrambled` in EvaluateMicro) -- evens out fitness across smaller scrambled counts.
- Metric = **P2 + N*S** (the `ladder = P2 + N*S`; Fitness in COHERENT = the pure coherence factor `(P2+N*S)/NORM`).
- Accept = the restored mode-split: descent compares peel `Fitness < Score`; COHERENT compares the STRUCTURE ladder `Fitness < 1 && Ladder <= ScoreLadder` (sideways on equal structure). GA SELECTION is separate: the sort breeds by Fitness, which in COHERENT is pure coherence. This ladder-sideways accept is what lets the endgame CLIMB (escapes peel local minima like the mono-twist); the peel-only accept (the abandoned "(b)" experiment) trapped there.

**THE BOTTLENECK -- where the next win is.** The coherence ladder climb is very slow and is dominated ENTIRELY by the FIRST rung, the scattered floor **1+1+1+1**: it held from ~1k GA to ~160k GA -- ~159k of the 180k, **~88% of the whole solve**. Everything above the floor is fast by comparison.

**FLATNESS IS A FEATURE -- a metric slope on the first rung BACKFIRES (2026-08-07, tested to conclusion).** We tried giving the flat `1+1+1+1` plateau a sub-gradient (an "orient" term: per-cubie L1 distance to the cluster's dominant orientation while building, to identity once a single block). On 2^4 it was NEUTRAL (first rung already cheap); on 2^5 -- its own target -- it was WORSE: stuck on `1+1+1+1` to ~260k (vs the ~159k baseline), and the tell was "rarely moves sideways." MECHANISM: a slope makes SELECTION converge the whole population onto the lowest-`orient` config -> diversity collapses -> the plateau's broad sideways exploration dies -> the RARE jump `1+1+1+1 -> 2+2+2+2` gets HARDER to find. So the flat plateau (which the 2+1+1==1+1+1+1 tie preserves) is a FEATURE: flat = no selection pressure = max diversity = wide search, exactly what a rare-maneuver exit needs. The first rung is NOT a "missing gradient" problem; it is a rare HARD JUMP that needs EXPLORATION. Do NOT shape the metric to slope the plateau (orient, variance, coupling-as-slope all collapse diversity). The real levers are DIVERSITY/exploration: bigger population, restart/diversify-on-stall (reseed/mutation injection), or a TARGETED seed of the all-pairs maneuver. Also learned: the gateway COLLAPSE (block -> solved) is a non-problem -- simple moves close it by chance, no identity-reference / phase-3 machinery needed. (Bug found en route: gateway detection must be `pieces==1` (single complete block), not `domCount==ns` (one orientation) -- moot now that orient is abandoned.)

**Why it's slow -- and why the tie is a FEATURE, not a bug (user corrected me 2026-08-06).** The productive endgame is the DOUBLING ladder via SYMMETRIC structures, NOT lone blocks among singletons:
  `1+1+1+1 -> 2+2+2 / 2+2+2+2 -> 2+2 / 2+0 -> 4+4 / 4+0 -> 8+0 -> (8+8) -> 16+0(=gateway) -> solved`.
`2+1+1` (a 2-block among singletons, S=2) is a SCATTERED TRAP -- forming one lone pair leads nowhere good. The metric DELIBERATELY ties it with 1+1+1+1 (N=5 both 50, N=4 both 36: the S-term +N cancels the P2 drop) so the search does NOT commit to it. So do NOT tip S below N to make `2+1+1 < 1+1+1+1` -- that OPENS the trap. The first productive move is the SIMULTANEOUS pairing `1+1+1+1 -> 2+2+2+2` (which the metric rewards: ladder 50 -> 38 for N=5), a big multi-pair jump; partial pairing is flat on purpose. So the 159k is a large-step, trap-guarded gradient -- the lever is FINDABILITY of the all-pairs maneuver (or a symmetric-only partial-progress reward that can't leak into 2+1+1), NOT flattening the S penalty.

**Near-gateway rungs (2^5, ladder = 2*(P2+N*S)):** `8+0 = 8+8 = 16` (a TIE, like k+0==k+k -- adding a symmetric partner is free), `16+0 = 12`, solved = 0. So 8+8 is already reachable as a SIDEWAYS (the coherent accept `Ladder <= ScoreLadder` admits equal); making it a STRICT rung (`8+8 < 8+0`) needs the old collateral/pairing weight back (D3's `2*collat`). SAFE to do (8+8 is symmetric, S=1 -- NOT the 2+1+1 trap). **16+0 must NOT read as solved:** it does only if the 16-block is the WHOLE active cluster (agreeAxes==0 -> P2=0 -> ladder=0); if the 2^5 cluster is 32 (gateway 16 = half), 16+0 is agreeAxes=1 -> ladder 12 > 0 -> correctly not-solved. Guard = the existing agreeAxes==0 full-cluster exclusion; keep it intact.
